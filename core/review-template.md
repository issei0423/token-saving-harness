# 見直しの係への頼み方（ひな形）

設計書・コード・文書の見直しを、観点ごとに複数の係へ割るときの形。照合する係（`verifier`）が読める形に、出力をそろえる。

## 割り方

- **観点で割る**（文書で割らない）。文書で割ると、文書をまたぐ矛盾が誰の担当にも入らない
- 1体の担当は、読む量でおよそ4000行まで。同時は4体まで（`graph.md`「実行する」）
- 観点ごとに「その道の目で見るときの例」を5〜10個書く。例に限らないと添える

## プロンプトに入れるもの

1. 持ち主の言葉（原文）
2. **守ること**
   - ファイルは書き換えない。git を操作しない。出力ファイルにだけ書く
   - 読む場所（worktree・ブランチ）と主な文書
   - プロジェクトの軸（何のためのものか。AGENTS.md・CLAUDE.md にある目的）。直し方の案は軸で選ぶ
   - 持ち主が確かめた読み方（蒸し返さない）
   - **既知を重ねない**：前の洗い出し・要決定事項・決定事項を先に読ませる。理由が誤っていると考えるときだけ「既知だが再考」
   - いまの本文だけを見る（改訂履歴・過去の版の記述は対象外）
   - 根拠を添える。確かめたら URL、確かめていなければ「推測」
   - 引用はそのまま、`ファイル:行` を添える。矛盾は両側を引く
3. **担当の観点**と、その道の目で見るときの例
4. **重さ**の定義（高：安全・情報の漏れ・法令とのずれ・実装できない矛盾／中：使う人が困る・届かない・食い違う／低：言葉の揺れ）
5. **出力ファイル**（スクラッチパッドの `review-<日付>/<id>-<観点>.md`）と、指摘ごとの形：

```
### <id>-01 （1行の見出し）
- 種類：矛盾／（その道）の目／抜け
- 重さ：高／中／低
- 場所：`文書:行`（矛盾なら両側）
- 引用：「…」
- 何がおかしいか：
- 使う人に起きること：（誰が・いつ・何に困るか）
- 根拠：
- 直し方の案：（最小の直し。どの文書のどの節をどう変えるか）
- 誰が決めるか：Claude で直せる／チーム／持ち主
- 既知か：新規／既知だが再考（どこで決めたか）
```

6. 最終メッセージは40行以内：件数（重さ別）、大事な5件、出力ファイルのパス、読みきれなかった範囲

## 終わったら

- 全部の出力ファイルを `verifier` に渡す（`graph.md`「照合する」）
- 残った指摘を、「直せる」「人が決める」に分けて実行の点にする
